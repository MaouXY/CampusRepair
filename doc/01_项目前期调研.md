# 项目前期调研

## 一、项目背景

高校校园中存在大量与后勤保障相关的维修场景，例如宿舍水电、教室多媒体设备、实验室基础设施、校园网络、空调、门锁、照明等。传统报修方式通常依赖电话、微信群、线下登记或后勤人员人工记录，虽然实现成本低，但容易出现信息不完整、分类不规范、派单不及时、处理过程不可追踪等问题。

随着校园数字化建设的发展，基于浏览器的在线报修系统可以让学生通过 Web 门户提交问题，维修人员通过 Web 工作台接单处理，管理员在后台统一查看工单流转情况。进一步结合大语言模型或智能分类技术后，系统能够对学生的自然语言描述进行辅助分析，自动识别故障类型、推荐紧急程度、生成工单摘要，从而降低用户填写成本和管理员分单成本。

本项目拟设计并实现一个基于 Spring Boot 和 Vue 的校园智能报修与工单调度系统，服务于学生、维修人员和管理员三类用户，形成从报修提交、智能辅助、工单分配、维修处理、评价反馈到统计分析的完整业务闭环。

## 二、研究意义

### 1. 实际应用意义

校园报修属于高频、低门槛、强闭环的后勤管理场景。系统上线后可以减少人工登记和线下沟通成本，提高维修响应效率，让学生能够实时查看工单进度，也让后勤管理人员能够掌握维修任务分布、处理时长和高频故障区域。

### 2. 工程实践意义

本项目覆盖学生 Web 门户、维修 Web 工作台、后台管理端、后端接口、数据库设计、文件上传、权限控制、工单状态流转、统计分析等常见 Web 系统能力，适合作为毕业设计进行完整工程实现。

### 3. AI 应用意义

校园报修描述通常具有口语化、非结构化特点，例如“宿舍水龙头一直滴水”“教室投影连不上”“楼道灯坏了”。AI 可以将这些描述转化为结构化工单信息，为分类、派单和优先级判断提供辅助建议。该 AI 应用与业务流程直接相关，不是单纯展示模型能力，因此更适合答辩说明。

## 三、现状分析

### 1. 传统报修方式

部分高校仍采用电话、线下登记表、微信群或人工转发的方式处理报修。该方式灵活但缺少统一的数据沉淀，常见问题包括：

- 报修信息不完整，地点、故障现象、联系人等字段缺失。
- 报修分类依赖人工判断，容易分错部门或延迟派单。
- 学生无法清晰查看维修进度。
- 管理员难以统计报修量、维修效率和高频故障点。
- 重复报修难以及时识别。

### 2. 普通在线报修系统

普通在线报修系统可以解决在线提交、状态跟踪和后台管理问题，但通常要求用户手动选择分类、优先级和故障类型。对于缺乏维修知识的学生来说，分类选择可能不准确，导致后续分派效率下降。

### 3. 智能化报修系统

智能化报修系统在普通系统基础上引入自然语言处理、关键词规则、大语言模型和 RAG 检索增强生成能力，对用户描述进行分类、摘要、优先级判断、相似工单匹配和知识库问答。其优势是能够提升报修信息结构化程度，并辅助管理员进行工单审核与派发。

## 四、用户痛点

### 1. 学生侧痛点

- 不清楚故障属于哪个维修分类。
- 口语化描述难以转换成规范工单。
- 不知道问题是否已经有人报修。
- 报修后缺少处理进度反馈。
- 简单问题无法获得即时自助建议。

### 2. 维修人员侧痛点

- 工单描述不标准，需要反复沟通确认。
- 优先级不清晰，任务处理顺序不明确。
- 缺少维修结果记录和历史参考。
- 重复故障或区域性故障难以快速发现。

### 3. 管理员侧痛点

- 人工审核和分类耗时。
- 派单规则依赖经验，管理成本较高。
- 缺少统计数据支撑后勤管理决策。
- 难以评估维修人员工作量和处理效率。

## 五、可行性分析

### 1. 技术可行性

后端采用 Spring Boot，可以快速构建 RESTful API、权限控制、文件上传、业务服务和数据库访问层。前端采用 Vue 系列技术实现学生门户、维修工作台和管理员后台。数据库使用 MySQL 存储用户、工单、分类、评价、公告、AI 调用记录等数据。报修图片、维修结果图片等非结构化文件使用 RustFS 作为对象存储，便于后续统一管理、访问和扩展。

AI 能力可采用“LangChain4j + 大模型 API + RAG 知识库检索 + 本地关键词规则兜底”的组合方案。在线环境下通过 LangChain4j 封装模型调用、提示词编排、向量检索和结果解析，完成分类、摘要、优先级判断和维修知识库问答；离线或接口异常时，使用关键词规则和固定知识库模板保证核心流程可用。

### 2. 经济可行性

项目主要依赖开源框架和常规云服务，开发成本较低。AI 调用可以通过限制调用场景、缓存结果和规则兜底降低成本。作为毕业设计，可使用模拟数据和有限范围测试完成验证。

### 3. 操作可行性

系统角色清晰，学生负责提交和评价，维修人员负责接单和处理，管理员负责审核、派单和统计。业务流程贴近校园生活，用户学习成本较低。

### 4. 答辩可行性

该选题避开了教务、成绩、学籍等强制度场景，不容易被质疑业务规则不符合学校真实流程。同时它又具备完整闭环和 AI 增强点，能够体现系统分析、工程设计和智能化应用能力。

## 六、同类系统对比

| 对比项 | 传统报修方式 | 普通在线报修系统 | 本项目智能报修平台 |
| --- | --- | --- | --- |
| 报修入口 | 电话、线下、微信群 | 网页表单 | 学生 Web 门户、维修工作台和管理员后台 |
| 信息结构化 | 低 | 中 | 高 |
| 故障分类 | 人工判断 | 用户手动选择 | AI 辅助分类 + 人工确认 |
| 优先级判断 | 人工经验 | 手动选择 | 关键词和 AI 辅助推荐 |
| 工单摘要 | 无或人工整理 | 用户原文 | AI 生成标准摘要 |
| 进度追踪 | 不稳定 | 支持 | 支持并保留状态流转 |
| 重复报修识别 | 困难 | 较弱 | 相似工单推荐 + RAG 历史工单检索 |
| 数据统计 | 困难 | 基础统计 | 多维统计分析 + 数据大屏 |

## 七、调研结论

校园维修报修场景具有需求明确、用户角色清晰、流程闭环完整、数据结构适中等特点，适合作为毕业设计项目。引入大语言模型辅助分类、摘要和优先级判断后，系统不仅可以完成常规信息化建设，还能够体现智能化服务能力。项目应坚持“AI 辅助、人工可修正、规则可兜底”的设计原则，既保证可演示性，也保证答辩时的合理性。
