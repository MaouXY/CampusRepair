# 开发计划与风险分析

## 一、总体开发思路

项目采用分阶段迭代开发方式，先完成基础业务闭环，再加入 AI 辅助能力和统计分析能力。第一阶段保证系统可运行、可演示；第二阶段完善智能化与管理能力；第三阶段进行论文材料、测试数据、答辩演示和细节优化。

开发顺序建议：

1. 数据库设计与基础表结构。
2. 后端用户、权限、工单、分类接口。
3. 学生端报修与进度查看。
4. 管理端审核、派单和分类管理。
5. 维修端接单、处理和结果填写。
6. RustFS 对象存储接入，完成报修图片和维修结果图片上传。
7. 基于 LangChain4j 实现 AI 分类、摘要、优先级建议和 RAG 检索增强。
8. 相似工单、RAG 知识库问答、统计分析和数据大屏。
9. 测试、演示数据、论文和答辩材料整理。

如涉及数据库建表或测试数据插入，应写入 SQL 文件，并在交付时说明执行顺序，由用户手动执行。

## 四、测试规划

### 1. 功能测试

测试重点：

- 学生能否正常提交报修。
- 图片上传是否限制格式和大小。
- AI 预分析是否返回分类、摘要和优先级。
- RAG 问答是否基于知识库返回答案和来源。
- AI 失败时是否启用规则兜底。
- RustFS 上传失败时是否记录运行日志并返回明确提示。
- 管理员是否能修改 AI 建议结果。
- 派单后维修人员是否能看到工单。
- 工单状态是否按规定流转。
- 学生是否只能查看自己的工单。
- 维修人员是否只能查看分配给自己的工单。
- 管理员统计数据是否正确。

### 2. 异常测试

测试场景：

- AI 服务超时。
- AI 返回非 JSON 内容。
- AI 返回 JSON 但字段缺失、枚举值越界或包含不允许字段。
- AI 首次返回不合法后 repair 成功。
- AI repair 后仍不合法并进入规则兜底。
- RAG 检索无结果。
- RAG 向量索引重建失败。
- RustFS 对象存储连接失败。
- 图片上传失败。
- 管理员派单给不存在的维修人员。
- 维修人员重复接单。
- 学生评价不存在或未完成的工单。
- 无权限访问他人工单。

异常测试要求：

- 接口返回明确错误提示。
- 数据库不产生错误状态。
- 应用运行日志记录业务场景、关键 ID 和完整异常信息。
- 需要业务留痕的场景写入对应记录表。

## 五、风险分析

### 1. AI 调用不稳定

风险说明：LangChain4j 调用的大模型 API 可能出现超时、网络异常、额度不足或返回格式不稳定。

应对措施：

- 设置请求超时时间。
- AI 分析结果继续使用 JSON 格式输出，但不能只依赖 prompt；优先启用 JSON mode 限制模型输出形态。
- prompt 中声明 schema、必填字段、枚举范围和禁止额外字段。
- 对返回内容做服务端 JSON 解析、DTO 反序列化和业务字段校验。
- 首次解析或校验失败时触发一次 repair 二次修复，修复仍失败才进入规则兜底。
- 失败时启用关键词规则兜底。
- 记录 AI 调用业务留痕。
- 记录 JSON 解析失败、schema 校验失败、repair 成功率和 fallback 次数等指标。
- 使用 `log.error(..., exception)` 记录完整异常栈。

### 2. RustFS 对象存储不可用

风险说明：RustFS 服务可能出现连接失败、权限配置错误、Bucket 不存在或文件上传失败。

应对措施：

- 启动时检查 RustFS 连接配置。
- 上传失败时返回明确错误提示。
- 文件上传异常必须记录业务场景、工单 ID、用户 ID、文件名和完整异常栈。
- 数据库只保存上传成功后的对象 key、访问地址和文件元数据。

### 3. AI 判断不准确

风险说明：AI 可能将故障分类或优先级判断错误。

应对措施：

- AI 结果只作为建议。
- 管理员审核时可手动修改。
- 保存 AI 建议值和人工最终值。
- 答辩时强调“辅助决策，不替代人工”。

### 4. RAG 检索结果不准确

风险说明：知识库内容不足、切片不合理或向量检索召回错误，可能导致回答依据不准确。

应对措施：

- 知识库由管理员维护并支持启用、停用。
- RAG 回答返回来源，便于审核。
- 检索结果为空时不让大模型编造答案。
- 高风险问题优先走安全提示和紧急报修建议。
- RAG 检索失败和索引重建失败必须写应用运行日志。

### 5. 业务范围过大

风险说明：如果同时实现采购、库存、预算审批、复杂派单策略，容易导致项目失控。

应对措施：

- 第一阶段聚焦报修闭环。
- 库存、耗材、催办作为扩展功能。
- 优先保证核心流程稳定可演示。

### 6. 前后端联调复杂

风险说明：学生门户、维修工作台、管理端和后端同时开发，接口字段不一致可能拖慢进度。

应对措施：

- 先确定接口文档和状态枚举。
- 后端优先提供 Swagger 或接口说明。
- 使用固定测试账号和测试数据联调。

### 7. 权限控制遗漏

风险说明：学生可能查看他人工单，维修人员可能操作未分配工单。

应对措施：

- 后端接口按角色校验数据范围。
- 关键操作校验当前用户与工单关系。
- 添加权限测试用例。

## 六、论文结构建议

毕业论文可按以下结构组织：

1. 绪论：研究背景、研究意义、国内外现状、研究内容。
2. 相关技术介绍：Spring Boot、Vue、MySQL、RustFS、LangChain4j、RAG、大语言模型、前后端分离。
3. 系统需求分析：角色分析、功能需求、非功能需求、业务流程。
4. 系统总体设计：架构设计、模块设计、数据库设计、接口设计。
5. 系统详细设计与实现：学生端、维修端、管理端、对象存储模块、AI 模块、RAG 知识库模块、统计模块、数据大屏。
6. 系统测试：测试环境、功能测试、异常测试、测试结果。
7. 总结与展望：项目总结、不足与后续优化方向。

## 七、答辩防守点

### 1. AI 判断错了怎么办

AI 分类结果只作为辅助建议，不直接替代人工决策。管理员和维修人员可以手动修改工单分类、优先级和分配对象，系统会保留最终处理记录。

### 2. 为什么校园报修需要 AI

校园报修中用户描述通常比较口语化，分类不规范，容易导致分派效率低。AI 可以对自然语言描述进行结构化处理，提高工单录入和流转效率。

### 3. 没有大模型 API 怎么演示

系统提供关键词规则兜底方案。即使没有网络或大模型服务不可用，仍然可以完成分类、优先级判断和报修提交流程。

### 4. RAG 和普通大模型问答有什么区别

普通大模型主要依赖模型已有知识，可能不清楚本校维修知识库和历史工单。RAG 会先检索系统内的知识库、历史工单和公告信息，再让大模型基于检索结果生成回答，并返回依据来源，能够减少凭空回答的问题。

### 5. 为什么不做教务或成绩系统

教务和成绩管理属于学校核心业务，流程规范复杂，容易涉及真实制度差异。校园报修更贴近日常生活，业务边界清晰，适合毕业设计完整实现。

### 6. 如何证明系统有实际价值

系统可以减少学生填写成本、降低管理员人工分类和派单成本，并通过统计分析帮助后勤部门发现高频故障地点和维修效率问题。
