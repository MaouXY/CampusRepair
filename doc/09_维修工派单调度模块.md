# 维修工派单调度模块说明（第二轮提质）

> 对应《项目提质规划》V2「AI 辅助调度版」中的「AI 推荐维修员」「AI 派单建议」，以及工程化要求的状态机、幂等、日志、测试。

## 1. 模块定位

校园报修系统原来只有「管理员人工挑维修员」。本模块把派单升级为**可解释的智能调度**：

1. **规则评分保底**：按维修员画像（部门、技能标签、是否参与派单、最大活跃工单数）+ 当前负载 + 历史质量 + 返工/退回记录，算出 Top3 候选与每人总分；
2. **AI 辅助决策**：候选 Top3 作为结构化上下文喂给大模型，由模型在候选范围内给出推荐人、派单说明与置信度，避免「模型凭空点名」；
3. **全过程留痕**：每次分析把候选评分快照落库，管理员事后能解释「为什么推荐他」。

关键设计原则：**AI 只做排序内的选择，不产生候选**。模型返回的 `suggestedWorkerId` 若不在候选集合内，一律回退到规则第一名并记录 WARN 日志。

## 2. 数据模型

| 表 | 作用 | 关键字段 |
| --- | --- | --- |
| `worker_profile` | 维修员派单画像 | `department_name`、`skill_tags`(JSON)、`dispatch_enabled`、`max_active_orders` |
| `worker_dispatch_score_snapshot` | 每次 AI 分析的候选评分快照 | `ticket_id`、`ai_analysis_id`、`worker_id`、各分项分、`total_score`、`rule_reason`、`ai_recommended` |

建表脚本：`sql/13_schema_worker_dispatch.sql`；演示数据：`sql/14_seed_worker_dispatch_demo.sql`。

## 3. 评分规则（总分满分 100，扣分上限 15）

| 维度 | 满分 | 规则 |
| --- | --- | --- |
| 技能匹配 `skill_score` | 40 | 40 × 命中技能数 / 所需技能数；所需技能来自分类映射 + 描述关键词（漏水、插座、网络、空调、门窗、公共设施等） |
| 部门匹配 `department_score` | 20 | 期望部门（分类→部门映射）一致得 20，否则 0 |
| 负载 `workload_score` | 20 | 20 ×（1 − 活跃工单数 / 最大活跃工单数），下限 0 |
| 历史质量 `quality_score` | 20 | 20 × 平均评分 / 5；无评价时给默认 12 分（不惩罚新人） |
| 返工退回 `penalty_score` | 最多扣 15 | 每次 `WORKER_RETURN` 或 `REQUEST_REWORK` 扣 3 分 |

排序：`总分 ↓ → 活跃工单数 ↑ → workerId ↑`（稳定可复现），取 Top3。
`dispatch_enabled = 0` 的维修员直接排除，不进入候选。

## 4. 端到端流程

```text
学生提交报修
  → 保存工单 + 绑定图片
  → 异步触发 AI 预分析（TicketAiPreAnalysisTrigger）
      → 规则评分得到候选 Top3（WorkerDispatchScoringService.plan）
      → 拼提示词：工单信息 + 报修图片 + 候选 Top3 + RAG 知识片段
      → 调用大模型（含 token 监控与降级，见 doc/10）
      → 保存 repair_ai_analysis + 候选评分快照
  → 管理员打开工单抽屉
      → GET /api/v1/admin/tickets/{id}/dispatch-suggestion（规则/AI 建议 + 推荐原因）
      → 点击「填入」一键选中推荐维修员
      → POST /api/v1/admin/tickets/{id}/assign（统一状态机校验：仅 PENDING_REVIEW → ASSIGNED）
```

## 5. 接口清单

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/admin/tickets/{ticketId}/dispatch-suggestion` | 派单建议：来源（AI / AI_FALLBACK / RULE）、推荐人、推荐原因、置信度、候选 Top3 |
| POST | `/api/v1/admin/tickets/{ticketId}/ai/analysis` | 手动触发 AI 预分析（含派单候选快照） |
| GET | `/api/v1/admin/tickets/{ticketId}/ai/analysis/latest` | 读取最近一次分析结果 |
| GET | `/api/v1/admin/workers/options` | 维修员下拉（含部门、技能、当前负载/上限） |
| POST/PUT | `/api/v1/admin/workers` | 维护维修员画像（部门、技能标签、是否参与派单、最大活跃工单数） |

`dispatch-suggestion` 的行为：

- 有 AI 分析（且状态为 `SUCCESS`）→ `recommendationSource=AI`，推荐理由 = AI 派单说明 + 规则依据；
- AI 降级过（`FALLBACK`/`FAILED`）→ `recommendationSource=AI_FALLBACK`，沿用规则兜底结论并注明；
- 还没分析过 → `recommendationSource=RULE`，直接给规则建议（**AI 不可用不影响人工派单**）；
- 当前无可用候选 → 返回空候选 + 中文提示，前端提示先维护维修员画像。

## 6. 日志与可观测性

统一 `scenario=` 前缀，便于排障：

- `admin-dispatch-suggestion`：生成建议（来源、候选数、推荐人、依据规则/AI）；
- `worker-dispatch-score`：技能标签 JSON 解析失败（含原始 JSON）；
- `dispatch-score-snapshot`：快照写入失败；
- `admin-ticket-ai-analyze` / `student-create-ticket-ai-pre-analysis`：AI 分析成功/失败/降级；
- `admin-ticket-ai-response`：历史快照回读异常。

## 8. 验收标准对照（提质规划 3.6）

| 验收项 | 实现 |
| --- | --- |
| 管理员能看到推荐人选和原因 | `dispatch-suggestion` 返回 `recommendedWorkerName` + `recommendedReason`，前端抽屉顶部展示 |
| 点击「一键填入」能自动选择维修员 | 候选表每行「填入」按钮 → `assignForm.workerId`，并校验该人仍在可派单列表 |
| AI 不可用时不影响人工派单 | 规则评分独立于 AI；AI 失败/降级/超预算均回退规则结果并写快照 |

## 9. 答辩演示路径（派单相关片段）

1. 学生提交带图片的报修 → 系统自动触发 AI 预分析；
2. 管理员打开待审核工单 → 看到「智能派单建议」：推荐维修员、推荐原因、候选 Top3（技能/负载/总分/规则原因）；
3. 点击「填入」→ 维修员被自动选中 → 审核通过并派单；
4. 说明「为什么是他」：技能匹配 40 + 部门 20 + 负载 20 + 质量 12 = 总分，以及 AI 在候选范围内做的选择。
