# 第三阶段 V3：数据治理与知识沉淀

> 对应《项目提质规划》V3「数据治理与知识沉淀版」：典型工单自动生成知识库草稿、月度维修报告、满意度与绩效分析、高发故障/高发地点统计、RAG 检索升级为真实向量模型。

## 1. 典型工单自动沉淀知识库

### 1.1 业务价值

知识库如果只靠管理员手工维护会很空。本功能把**已闭环的优质工单**自动转成知识草稿，管理员只做审核，知识库就能随业务自然增长。

### 1.2 闭环流程

```text
学生评价完成（工单 → COMPLETED）
  → 事务提交后异步触发 RagKnowledgeDraftTrigger（不阻塞评价主流程）
  → 判定是否值得沉淀（见 1.3）
  → AI 生成标题+正文（token 预算不足 / AI 异常 → 规则模板兜底）
  → 落库 rag_knowledge_draft（PENDING_REVIEW）
  → 管理员审核：通过 → 生成 rag_knowledge_document + 切片 + 同步 Milvus
                驳回 → 记录驳回原因，不产生知识
```

### 1.3 沉淀条件（满足其一）

- 学生评价 ≥ 4 分；
- 处理结果完整（≥ 8 字）且同时具备处理备注或结果图片。

不满足条件时不生成草稿（记录 `reason=not-worth-precipitating` 日志），避免把无效工单堆进知识库。

### 1.4 数据表

`rag_knowledge_draft`（`sql/18_schema_rag_knowledge_draft.sql`）：

| 字段 | 说明 |
| --- | --- |
| `source_ticket_id` | 来源工单 |
| `title` / `content` | 草稿标题与正文（结构化：适用场景/故障现象/可能原因/处理步骤/注意事项） |
| `status` | `PENDING_REVIEW` / `APPROVED` / `REJECTED` |
| `created_by_ai` | 1=AI 生成，0=规则模板兜底 |
| `generate_source` | `AI` / `AI_DEGRADED` / `RULE` |
| `review_remark` / `reviewed_by` / `reviewed_at` | 审核留痕 |
| `knowledge_document_id` | 审核通过后生成的知识文档ID |

### 1.5 幂等与一致性

- 同一工单已存在非驳回草稿 → 直接复用，不重复生成；
- 重复审核通过 → 返回已有结果，不重复建文档（`knowledge_document_id` 不变）；
- 已驳回的草稿不允许再审核通过（返回 409），已通过的草稿不允许驳回。

### 1.6 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/admin/rag/drafts?page&size&status` | 草稿分页（可按状态筛选） |
| GET | `/api/v1/admin/rag/drafts/{draftId}` | 草稿详情 |
| POST | `/api/v1/admin/rag/drafts/generate?ticketId=` | 手动为某工单生成草稿 |
| POST | `/api/v1/admin/rag/drafts/{draftId}/approve` | 审核通过并入库切片、同步向量库 |
| POST | `/api/v1/admin/rag/drafts/{draftId}/reject` | 驳回并记录原因 |

## 2. 绩效与满意度分析

`GET /api/v1/admin/stats/worker-performance?days=30`，按维修员输出：

| 指标 | 说明 |
| --- | --- |
| `completedCount` | 区间内完成工单数（按 `processed_at` 归期） |
| `avgProcessMinutes` | 平均处理时长 =（`processed_at - assigned_at`）均值，单位分钟（无数据返回 0） |
| `avgScore` / `goodRate` | 平均满意度（5 分制）与好评率（≥4 分占比） |
| `evaluationCount` | 参与统计的评价条数 |
| `returnCount` / `reworkCount` | 区间内维修员退回次数 / 学生返工申请次数 |
| `activeCount` | 当前在手工单数 |
| `overdueCount` | 当前在工单中已超过 SLA 的数量 |

排序规则：完成量降序 → 平均满意度降序 → 员工ID，便于做「派单倾斜」和绩效复盘。

## 3. 高发故障与高发地点统计

`GET /api/v1/admin/stats/hotspots?days=30&limit=5`

- 按区间内工单（`created_at` 或 `processed_at` 落在区间）聚合分类与地点，输出 TopN 及工单量；
- 返回 `totalTickets` 便于计算占比；
- 用于安排巡检、备件储备与知识库补充优先级。

## 4. 月度维修报告

`GET /api/v1/admin/stats/monthly-report?month=2026-09`（`month` 缺省为当月，非法值自动回退当月）

报告内容：

1. 规模指标：新增、完成、驳回工单数；
2. 效率与质量：平均处理时长、平均满意度、好评率、超时率（完成工单中 `processed_at > sla_deadline_at` 的占比）；
3. 结构指标：高发故障 Top5、高发地点 Top5、维修员完成量 Top5；
4. **AI 运营分析建议**：把上述指标作为上下文交给大模型输出 150–250 字结论 + 改进动作；`aiDegraded=true` 表示本次走的是**规则模板兜底**（AI 不可用或 token 预算已耗尽），页面上会带「规则模板兜底」标签。

## 5. RAG 检索升级为真实向量模型（核对）

真实向量检索能力已经内置，可通过状态接口一键核对：

`GET /api/v1/admin/rag/vector-status`

| 返回字段 | 含义 |
| --- | --- |
| `embeddingProvider` / `embeddingModel` / `dimension` | 当前 Embedding 提供方（`ARK_OPENAI` 真实向量模型 / `LOCAL_HASH` 本地哈希离线兜底）、模型名与向量维度 |
| `milvusEnabled` / `collectionName` | 向量库开关与集合名 |
| `documentCount` / `chunkCount` | 知识文档数、切片总数 |
| `syncedChunkCount` / `pendingChunkCount` / `failedChunkCount` | 切片同步状态（成功/待同步/失败） |
| `hybridEnabled` / `rrfK` | 混合检索开关与 RRF 常数 |
| `rerankEnabled` / `rerankModel` | 重排开关与模型 |
| `message` | 中文结论与建议（如「存在 N 个切片同步失败，建议重建」） |

切换到真实向量模型的步骤：

```text
1) 配置 app.agent.rag.embedding.provider=ARK_OPENAI（或 OPENAI_COMPATIBLE）
   + base-url / api-key / model；
2) 配置 app.agent.rag.milvus.dimension 与所选 embedding 模型维度一致（当前默认 2560）；
3) 启动 Milvus，配置 app.agent.rag.milvus.* ；
4) 在知识管理中逐个「重建」或在草稿审核入库时自动切片同步；
5) 调 /admin/rag/vector-status 确认 synced 数等于 chunk 数；
6) 用 RAG 评测接口跑一次 dataset=campus-repair-builtin，对比 LOCAL_HASH 与真实向量模型的
   HitRate/Recall/MRR/nDCG，即为「升级收益」的量化证据。
```

若向量维度与既有集合不一致，`recreate-on-dimension-mismatch=true` 时会自动重建集合（开发期便利），生产环境建议置为 false 并手工迁移。

## 8. 答辩表述建议

> 系统在完成工单闭环后，会把评价 4 分以上的优质工单通过大模型整理成结构化知识草稿，管理员审核后自动切片并写入向量库，形成「业务产生知识、知识反哺业务」的正循环；同时提供维修员绩效与满意度分析、高发故障与地点统计，并按月生成运营报告，报告结论由大模型基于真实统计指标生成，模型不可用时自动退化为规则模板，保证系统始终可用。
