### 3.4 混合检索 + RRF 生效证据

- 融合算法：`RagFusionService`，`score = Σ weight / (k + rank)`，`DEFAULT_RRF_K = 60`（取自 Cormack et al. 2009），来源标记 `KEYWORD` / `VECTOR`。
- 重排融合：`RagKnowledgeService:251/457`，`rerankBlendWeight` 默认 **0.7**，即最终分 = 0.7×重排分 + 0.3×RRF 分。
- 实测：评测逐条 `retrievedChunks.source` 中同时出现 `KEYWORD`、`VECTOR`、`KEYWORD+VECTOR`，证明两路召回与融合在真实链路生效（不是只写代码未接线）。

## 4. 本次修复的缺陷

### 4.1 现象

把维修员 10002（李师傅）的 `dispatch_enabled` 置 0 后，重新请求 `GET /api/v1/admin/tickets/{ticketId}/dispatch-suggestion`，候选列表仍返回 3 人（含李师傅），与 `doc/09` §3「`dispatch_enabled=0` 的维修员直接排除，不进入候选」不一致。

### 4.2 根因

工单已存在 AI 预分析时，`WorkerDispatchService.resolveCandidates` 直接使用 `worker_dispatch_score_snapshot` 的历史快照（`loadSnapshotCandidates`），只做了「快照为空则回落规则评分」的处理，**没有用当前画像复检 `dispatch_enabled`**；而 `WorkerDispatchScoringService.score()` 只在规则评分路径上过滤。于是「分析后关闭派单」的维修员仍能从快照里冒出来。

### 4.3 修复

- `WorkerDispatchScoringService.filterDispatchAvailable(candidates)`：按当前数据过滤——账号 `role=WORKER && enabled=1 && deleted=0`，画像 `deleted=0 && dispatch_enabled=1`（无画像视为可用，与规则评分口径一致）。
- `WorkerDispatchService.resolveCandidates`：快照候选先过该过滤器；被过滤时打 WARN；若过滤后为空则回落规则评分（规则评分同样会排除他们，最终走「暂无可用维修员」的中文提示）。

### 4.4 验证

- 服务端日志：`dispatch snapshot candidates filtered by current worker profile, … ticketId=2098426608888074242, aiAnalysisId=2098426912874450945, before=3, after=2`
- 接口实测：关闭后候选只剩 赵师傅(32)、周师傅(24)；恢复后候选重新出现 3 人。
- 新增回归用例：`WorkerDispatchServiceIntegrationTest#shouldExcludeWorkerAfterDispatchDisabledEvenWhenSnapshotExists`（造 AI 分析 + 快照 → 关闭派单 → 断言候选中不含该维修员且推荐人不等于他）。
- 全量：`Tests run: 106, Failures: 0, Errors: 0`（原 105 + 新增 1）。
